# Wishtaday 商品化完善建议

日期：2026年10月24日。供产品负责人确定首发范围与分批开发顺序。

Wishtaday 已有可以实际交付的产品基础：秘书分工、部门协作、联网调研、文件处理，以及从视频制作到预览、下载、归档的链路。当前更适合定位为内部试用版；完成下述门槛后，可进入小范围邀请测试，再进入公开收费。现阶段不宜承诺“所有岗位都能独立完成工作”或“大量用户随时稳定使用”。

最需要加强的是五件事：新用户独立上手、成果质量验收、可复用的业务知识、可核对的收费、生产环境稳定性。商品成熟度以用户能否持续获得合格成果来判断，不能由员工数量、技能数量或测试通过数量直接推算。

本轮只检查和提出方案，新增本文与评审图片；没有修改代码、业务数据、办公室动画、员工技能绑定或模型配置，也没有对外发布。

## 1 产品定位与首发范围

建议首批用户聚焦中文的一人经营者、独立顾问和小型内容运营团队。这个定位是待用户访谈验证的产品假设，尚没有付费转化数据证明。

对外可以表达为：**把一个经营需求，变成可以审阅、修改、下载和继续复用的工作成果。** 办公室与员工形象作为品牌特色保留；每位员工同时显示明确岗位、可交付内容和当前可用状态，让新用户不用先记住人物名字。

首发重点打磨三条流程：

| 场景 | 用户提供什么 | 应交付什么 | 首发边界 |
|---|---|---|---|
| 竞品与市场调研 | 产品介绍、目标市场、待回答问题 | 带来源的对比表、决策建议、未解决问题 | 提供证据与分析；不保证获得付费或不可访问资料 |
| 内容与短视频制作 | 产品资料、目标受众、参考素材、预算 | 文案、分镜、可预览成片、修改版本、下载文件 | 先以制作和下载为完整承诺；发布平台逐一实测后单独开放 |
| 企业资料与周期总结 | 获准使用的资料、任务记录 | 可追溯的资料问答、摘要、周报 | 先明确资料权限和更新机制，再扩大自动化范围 |

程序开发、客户拓展和合规分析保留入口及已有能力，但按照真实可用范围标明测试中或能力限制。代码执行环境、真实平台发布及专业结论不应仅因存在页面就成为首发承诺。首期不同时追求完整编程平台、专业剪辑软件、客户管理系统和所有社交平台接入。

4yi 的商业目标可以与这一定位结合：用户因成果有用而持续使用，带动可持续的 API 消费。核心指标应是“被用户采纳的成果”和“再次使用”，同时监测单份成果的成本。无效重试、重复传入大量资料、无关后处理增加的调用量应当下降。

## 2 已有能力和真实边界

以下区分本次看到的页面与代码、此前实际验收，以及尚未验证的生产条件。

| 领域 | 已有基础 | 商品化仍需补齐 |
|---|---|---|
| 秘书和协作 | 对话、待确认分工、后台依赖队列、前序成果交接、部分失败恢复 | 企业业务知识、项目分组、准确的当前状态、用户易懂的统一任务入口 |
| 员工和技能 | 员工独立技能绑定、档案管理、分类推荐、自检历史 | 技能是否真正有效的评价、依赖是否就绪、可执行能力说明；保留现有绑定 |
| 调研 | 搜索、正文读取、来源记录、结构化报告、归档 | 按问题覆盖证据、来源质量、补查、部分完成状态、结论与来源的对应 |
| 资料 | 上传、解析、OCR、比对、归档检索、容量和回收站 | 项目知识与资料版本、授权共享、可管理的记忆、更适合视频业务的存储方案 |
| 视频 | 自动保存、规格继承、裁切预览、字幕配乐预览、单镜头替换、中文配音、版本与定稿、下载归档 | 跨服务器配音、旧视频语音识别、品牌一致性、质量评测、收费与媒体权限 |
| 安全与恢复 | 凭据防护修复、权限基础、隔离恢复演练、本机守护 | 真实生产环境验收、多企业媒体隔离、异地备份、告警、发布回滚 |
| 账号与费用 | 本地登录、工作空间、成员邀请和角色、用量记录、文字每日额度 | 公开注册找回、正式登录验收、支付退款、金额预算、逐任务对账 |

此前六项改进验收记录为标准测试445项通过、61项跳过，视频浏览器专项24项通过。它们证明了相应本地功能，不代表全部业务质量或生产容量。本次没有重新付费生成视频，也没有重跑整套自动化测试。见[六项功能验收](six-improvements-2026-10-23.md)。

## 3 优先完善的功能

“首发前”表示相应能力对外承诺前必须完成；“试用期”表示邀请用户试用时迭代；“后续”表示暂不阻塞首发。工作量小、中、大只用于相对排序，不是工期承诺。

| 编号与优先级 | 现状与建议 | 验收标准 |
|---|---|---|
| P01 首发前／中：首次使用 | 已有创建工作空间，但没有面向经营场景的完整引导。增加用途选择、示例任务、资料准备和试用额度说明；默认服务由平台提供，专业用户再选择自带密钥 | 新用户不用讲解即可发起一项支持的任务；缺资料时知道该补什么；模拟演示与真实付费执行明确区分 |
| P02 首发前／中：任务需求单 | 已有分工草稿。补充目标、受众、交付格式、验收要求、预算、资料范围，并保存为任务快照 | 修改分工后要求不丢；执行者收到同一版需求；已知信息不反复询问 |
| P03 首发前／中：成果验收 | 部分流程已有审批、规格检查和定稿，尚未形成统一质量状态。区分执行状态与成果质量，增加完整交付、部分交付、待补充、待用户验收 | 缺关键证据的调研不显示为完全交付；规格失败的视频有明确处置；可以反馈修改并保留旧版 |
| P04 首发前／中：公司和项目资料 | 现有员工不能可靠知道本系统能力。先接入安全的产品能力摘要，再增加企业介绍、品牌规则、目标客户和项目资料 | 秘书能说明可用能力及限制；员工引用所用资料和版本；不能越过企业、用户或项目权限 |
| P05 首发前／中：统一任务管理 | 已有搜索和任务列表。补项目归属、负责人、待我确认、待补充信息、错误恢复入口，以及任务直达链接 | 从秘书、员工、资料室打开的是同一任务；刷新仍在原任务；超时可查原请求，避免重复花费 |
| P06 试用期／中：模板复用 | 已有提示词快捷模板，仍需可重跑的完整流程模板 | 成功流程可另存模板；下一次只填写变化的参数；不带入上个客户的私有资料；模板有版本和适用范围 |
| P07 试用期／中：通知与周期执行 | 已有到时写入秘书对话的提醒。增加统一待办和完成／失败通知，再增加周期任务 | 提醒与自动执行分别说明；可暂停、查看下次运行、避免重复执行；对外发布继续人工确认 |
| P08 首发前／中：成员能力与协作权限 | 已有所有者、管理员、成员，但秘书聊天和部分任务接口限所有者／管理员；当前资料室也明确为个人可见。需要定义成员是否能独立交任务、使用哪些额度、共享哪些成果 | 按角色逐项验收，避免为正常工作赋予管理员权限；共享须明确授权；移除成员后不能继续访问共享内容 |
| P09 首发前／中：数据管理 | 已有回收站和引用保护。补任务与文件的保留规则、账户数据导出／注销流程、存储计量范围 | 用户知道哪些文件能清理；删除项目不会悄悄破坏保留成果；文件、原始媒体与备份的保留边界明确 |
| P10 首发前／中：帮助和人工支持 | 当前主要依靠开发者解释。建立帮助入口、问题反馈、错误编号、任务诊断包 | 用户可报告某个任务的问题；诊断包脱敏；客服能定位问题且不能默认查看所有企业内容 |

P08 的角色限制是代码观察，尚未作为普通成员重新做全流程测试。应先确定产品规则，再判断具体接口需开放还是页面需明确提示。不能简单放宽所有权限。

## 4 需要加强的算法与任务执行方法

这里的“算法”指模型如何拿资料、分解任务、使用工具并检查结果。首阶段优先改进这些环节；是否更换模型或训练专用模型，应由后续实测决定，本轮不调整模型配置。

| 编号与顺序 | 要加强的机制 | 建议实施与衡量方式 |
|---|---|---|
| A01 第一批：事实上下文 | 员工知道正在服务谁、有哪些可用能力、任务做到哪一步 | 分开提供平台能力、企业资料、项目资料、最新任务状态。状态从真实记录读取；不能从旧聊天猜测。能力摘要注明版本，不含密钥 |
| A02 第一批：研究覆盖 | 当前最多3组主题，每组最多尝试2次网页读取，全任务最多6次；一组有来源就可标记完成 | 将需求拆成待回答问题，给每项绑定证据；未覆盖的关键问题优先补查。在费用与时间上限内重试或更换官方来源，达到上限显示部分交付 |
| A03 第一批：证据质量 | 当前检查来源存在与正文读取，但这不能证明结论由该来源支持 | 为主要结论保存原文片段、来源类型、日期和适用范围。区分厂商宣传、实测和独立评价；同一内容的转载去重。不要把一个论坛帖当成广泛用户共识 |
| A04 第二批：相关资料检索 | 当前正式档案使用关键词命中排序，最多取4份；具备检索基础，但近义词和跨文档问题可能漏召回 | 先用真实问题建立检索测试，再评估关键词与语义检索结合。语义检索是按意思找资料；重排序是对候选资料再次排优先级。权限过滤必须先于内容进入模型 |
| A05 第二批：长对话与记忆 | 秘书当前取最近20条消息，任务上下文按字符上限截取，长期使用可能遗漏新近重要信息 | 保留需求和约束摘要，按任务取最新状态，原始来源仍能回查。用户可以查看、更正、删除长期偏好；冲突信息按来源和新旧版本处理 |
| A06 第三批：成本与模型选择 | 已有按部门配置和文字额度；尚缺覆盖完整任务的金额控制和质量反馈 | 先记录每一步耗时、成本与结果，再在获准模型范围内按任务需求选择。简单处理使用确定性代码；缓存按租户和资料版本隔离；重试有上限。采购价未知时不能保证金额预算精确生效 |
| A07 持续：执行恢复 | 已有持久队列、防重复和失败恢复，不需重写整套系统 | 补全取消、断点接续、未知结果对账和并发公平性。取消应解释上游已开始的调用是否仍会计费；对外发布不能因超时盲目重发 |
| A08 视频质量批次：一致性与检测 | 当前真实测试证明生成、播放和导出可用，未证明所有场景都达到宣传质量 | 生成前检查分镜、品牌资料、文字长度与比例；生成后检查黑帧、音量、字幕边界与规格。人物、商品外观和风格一致性需要人工样本评分；不自动重做不满意片段产生费用 |
| A09 从第一批开始：固定质量测试 | 工程测试较多，但真实业务成果质量仍缺统一基线 | 固定一组需求和验收标准，改动前后重复执行，记录首次可用率、事实错误、耗时、成本和人工修改量。代码规则、模型辅助检查与人工评审结合，避免模型自己说合格就算合格 |

A02 是这次竞品调研不足的具体工程原因之一，不等于唯一原因。网页可访问性、搜索结果质量和任务范围也会影响结果。不能简单把读取数量调大后就宣称解决。

在正式训练或微调模型前，先积累用户授权的成功与失败样例、修改原因和稳定评分办法。现阶段尚无数据证明微调比改进检索、上下文和执行控制更划算。

## 6 收费与4yi的配合方式

建议先验证两种清晰的使用方式：普通用户使用平台提供的服务额度；已有4yi账户的专业用户在明确授权后关联自己的账户。不要让普通用户在第一次使用时同时学习模型、密钥、代理和部门档位。

首发可以采用“软件服务费加明确的使用额度”的方向，具体售价等待成本样本与用户访谈后制定。视频单独展示消耗规则，避免把文字词元和视频生成混成一个难以理解的指标。BYOK指用户自带模型密钥，它的服务费与上游模型费用需要分别说明。

收费前需要完成：

1. **真实计量**：每次调用关联用户、任务、步骤和服务商请求编号；文字、图片、视频、语音及工具费用分别记录。
2. **价格版本**：明确单位、币种、税费口径、采购价和售价的生效时间；上游价格变更不能悄悄改写历史账单。
3. **金额预算**：开始前显示可信估算或估算区间，先预留额度、完成后结算；无法获得可靠价格的功能不能承诺精准硬上限。
4. **付款闭环**：支付结果、重复回调、防重复入账、退款、订单记录、套餐变化、欠费处理和开票需求。付款页面存在不等于支付已验收。
5. **失败规则**：区别未执行、上游已收费但结果失败、用户不满意重做；说明何时退费、何时需要人工核对。不先承诺所有失败免费。
6. **自助管理与支持后台**：用户看余额、任务账单和导出；运营人员看异常账单、成本、投诉与退款记录，操作留痕并受权限限制。

单份合格成果成本，应计入为得到它所发生的全部尝试：模型、搜索、媒体存储、下载流量、服务器和人工支持。评价盈利能力时，还要考虑支付手续费与退款。目前缺少真实采购价格、支付数据和足够用户样本，不给出毛利百分比或建议售价。

4yi账户、余额、价格和账单能否通过接口授权关联，本次未核验；这是商业化实施前需要确认的集成条件，不应假定已经存在统一账户能力。

## 10 如何判断可以开始公开收费

以下是建议的内部验收目标，尚未达成，也不是行业平均值。样本不足时不做百分比宣传。

1. **真实用户独立上手**：邀请约10名目标用户，记录从进入产品到拿到首份可用成果的步骤、时间、求助次数和退出原因。先在真实环境试用，再讨论购买意愿；不要只采访熟悉开发过程的人。
2. **固定场景重复验证**：三条首发流程各准备10个不同难度任务，并重复运行。分别统计完整交付、部分交付和失败；目标可先设为至少27／30能达到预先约定的验收标准，同时必须如实标注所有未完成任务。后续按场景、版本与样本量披露结果。
3. **关键错误零容忍**：测试中发现越权取资料、凭据泄露、无确认发布、重复扣款或静默丢数据，暂停扩大测试并修复，不用总通过率抵消。
4. **输入及时反馈**：建议输入与点击反馈目标在约100毫秒内，95%的提交在1秒内出现已接收或明确错误；生成耗时另计。该目标需在目标设备与网络实测，不能把等待模型的时间伪装成固定进度百分比。
5. **账单可对上**：每笔可收费执行都有对应记录，未知费用进入待核对；试用额度、退款和重复回调测试通过。未核对的调用不能直接算已结算收入。
6. **持续使用的证据**：观察试用用户是否在7天、30天内主动回来完成第二项、第三项工作，分别记录留存、付费意愿和主动推荐。首批样本只用于发现问题，不据此宣称市场需求已经验证。
7. **运行与恢复**：完成连续运行、断网、服务商超时、重启、升级失败和隔离恢复演练，并记录可接受的数据损失窗口与恢复时间。

长期看五个数字即可先形成判断：每周被采纳成果数、首份成果完成时间、任务首次可用率、每份合格成果总成本、用户再次使用比例。API消耗作为成本和收入的解释指标，与这些结果一起看。
