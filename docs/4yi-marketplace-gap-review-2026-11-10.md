### 免费使用的额度设计

已有按企业和任务的预算能力，但不能把它当作提供者全部安装实例共用的总预算。接入时应覆盖每用户的每日额度、图片/视频次数与并发，以及提供者全局额度和暂停入口。若采用多个安装实例，全局上限应由平台网关或共享的服务端预算系统统一执行；不能依靠各实例各自计数，导致重复放大额度。供应商价格未配置时，不能声称已经精确按金额拦截，应采用可核验的调用次数、Token 或供应商硬限额。

### 接入顺序及边界

1. 整理可重建的发布版本并修复当前高危依赖。2026-11-11 主站 `npm audit --omit=dev --json`：高危 1、中危 4、低危 2；本次未升级。
2. 实现 4yi 身份验证、提供者模型凭据适配和免费额度控制；真实模型选择及技能绑定保留。
3. 补齐视频等内部服务镜像、数据卷、初始化、迁移、备份和恢复，随后提供可执行的根目录声明。
4. 平台 DEV 安装：实际验证两个账号/组织的权限、提供者费用归属、完整视频流程、重启与升级恢复。真实调用前确认测试额度，正式对外开放仍由用户确认。

未验证：自有平台部署版本、签名注入支持、提供者密钥与平台安装令牌的优先关系、服务和存储上限，以及共享或独立实例的最终选择。无需用户在聊天中提供密钥。

## 建议采用的首版安装方式

建议先采用“每个客户组织安装一套独立 Wishtaday”的方式。即一家客户有自己的办公室和数据，并在这套实例内管理多位用户及 AI 员工。这与参考指南的 Dedicated 路径一致，也贴近本项目现有的企业视频服务隔离约束。Dedicated 指为每个安装组织提供独立的应用实例。

需要明确平台组织与 Wishtaday 工作空间的对应关系。当前一个账号可以创建多个工作空间，位置为 `apps/api/src/app.mjs:158`；每个工作空间的权限和视频服务绑定仍要正确处理，不能默认它们都等于安装组织。

本地现有业务继续保留。市场新安装只带产品模板、岗位与允许分发的角色素材，不能打包本地客户资料、聊天记录、模型密钥和代理会话。旧数据迁移是单独流程，尤其不能丢失解密现有配置所需的主密钥。

第一版需要按实际验收结果标明能力。若目标平台尚不能提供配音或代码执行环境，可以在发布说明和产品能力中明确暂不可用；不能保留可点击的功能并声称已经可用，也不应把宿主机控制权限直接暴露给主站来绕过隔离要求。

## 推荐执行顺序与完成标准

1. **接入设计和发布版本。** 整理当前代码及素材，固定提交；确认一组织一实例、内部服务和存储关系，编写部署声明候选。完成标准是平台能正确识别服务与配置，不包含个人密钥。
2. **身份和模型适配。** 增加 4yi 身份验证、组织与成员映射、模型槽位和安装令牌来源。完成标准是两个组织访问互不串数据，真实任务用安装者的模型权限和额度。
3. **运行与数据适配。** 打包完整视频服务，补齐 Linux 能力，接好持久化及首次初始化，修复高危依赖和素材访问问题。完成标准是干净环境能安装，重启后数据可读，更新失败能恢复。
4. **DEV 真实安装验收。** 从市场安装并完成“秘书接需求 → 调研 → 制作视频 → 剪辑预览 → 下载 → 归档”，检查取消、失败恢复、刷新和更新；使用不同组织及同组织不同账号验权限。不能用示例数据或单元测试替代。
5. **发布准备。** 完成平台的实际发布门槛、费用演练、套餐与可见范围，准备介绍、截图、支持渠道及已知限制；提交验收结果后由用户确认公开发布。

下一步优先做第 1 至 3 项的适配即可，不必为了接入市场改办公室动画、重新安排员工技能或扩大角色库。第一步声明工作较小，主要工作量在身份与模型连接、多服务安装和数据生命周期。
